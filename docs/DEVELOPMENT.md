# Build and test

Dictate & Delegate is an Android app (package `app.driftdictation`, kept from when it was called Drift, so updates install over it) (Java 17, Android SDK 36, AGP 8.13.2, Gradle 8.13). Set `JAVA_HOME` and the SDK path in a local `local.properties`. The Gradle wrapper is included; production has no external runtime dependencies.

```sh
./scripts/build.sh            # unit tests, lint, debug APK
./scripts/device-test.sh      # instrumented tests against a fake OpenRouter, a fake bb and a fake ntfy
```

UX checks by a persona agent on the emulator: [scripts/qa](../scripts/qa/README.md).

The debug APK is `app/build/outputs/apk/debug/app-debug.apk`. Android tests require a disposable Android 16 emulator: they replace the OpenRouter key and manipulate synthetic history, audio, permission grants, the clipboard and Quick Settings. Never run them on a phone with real Dictate & Delegate data. `device-test.sh` starts `scripts/fakes/fake_openrouter.py` on `DRIFT_TEST_PORT` (default 8797), forwards it with `adb reverse` and builds the app with `-PopenrouterUrl=http://127.0.0.1:8797/api/v1`. Tests save a fake key, queue transcripts, Jev answers (`decide`) and replies through the fake's `/test/script`, and read what the app sent from `/test/requests`. The fake reports fixed costs ($0.001 per transcription, $0.00002 per Jev decision, $0.0003 per text call). No provider calls, no charges. `scripts/fakes/fake_bb_mcp.py` stands in for bb's MCP server on the next port (`DRIFT_TEST_PORT + 1`, also forwarded): it answers `initialize`, `tools/list` and `tools/call` for `run`/`read`, recognises snippets by the bb command they call (`thread spawn`, `thread tell`, `thread show`), logs them at `/test/requests`, and takes queued failures at `/test/fail` and a required token at `/test/config`. `BbFlowTest` connects to it in custom-address mode. `scripts/fakes/fake_ntfy.py` (`DRIFT_TEST_PORT + 2`) serves a topic's JSON stream and polls, takes test publishes, and logs subscriptions. `PanelTest` drives the floating panel against `TestPadActivity` (a text field in the test APK): Insert and replace in place through the Accessibility service, the clipboard fallback, choices made while recording, the volume key (key events handed to `TalkAccessibility.onKeyEvent`; the emulator has no hardware volume key that reaches the accessibility filter), the chief's text back and ntfy's Copy broadcast. Pass `-e shots true` to save screenshots on the device under the app's `files/panel`. Tests read the clipboard only with Dictate & Delegate in front, since Android blocks clipboard reads from the background.

To sign a release, create `.signing/release.jks` with alias `drift`, put its password in `.signing/password`, then run `./scripts/release.sh 2.0.0 13` (version name and code). It writes a signed APK and an AAB to `dist/`. Both files are ignored.

Releases are normal releases (no betas), plain versions: `scripts/publish.sh android 3.3.0 55 notes.md` builds with `release.sh`, tags `v3.3.0`, pushes and publishes the APK with `SHA256SUMS` as the latest release; `scripts/publish.sh mac 0.2.0 notes.md` does the same for the Mac app (tag `mac-v0.2.0`). The apps update themselves from these (`Updates`): about once a day and with Settings → About → Check for updates they read GitHub's release list (anonymously), take the newest release with a plain tag for their platform, and on Update download it, check it against `SHA256SUMS` (or GitHub's digest) and that it's signed with the installed app's key, then install it (Android: `PackageInstaller`, which asks to confirm; the Mac: replaces the app and restarts it).

Translations: UI text stays English in code as `tr("…")`. After adding or changing a text, run `scripts/i18n.py extract`, then `OPENROUTER_API_KEY=… scripts/i18n.py translate` to fill the seven other languages (it also drops texts the code no longer uses); `I18nTest` fails when one is missing. Review German by hand.

Network: the app talks to OpenRouter (`OpenRouter`, base URL `BuildConfig.OPENROUTER_URL`, set with `-PopenrouterUrl=`; default `https://openrouter.ai/api/v1`), with the user's own key from `Vault`. Speech goes to `/audio/transcriptions` in chunks of about two minutes. Jev (`Jev`, `~typesafe/jev-latest`, 3 s timeout) goes to `/api/alpha/decisions` with up to three questions: `refine` and `template` (a choice over the template names), and `chief` only when the chief's name (`Profile.chiefName`) appears in the transcript (`Jev.mentions`: whole word, possessive, -y/-i/-ie variants); the question carries the name. Refine starts at 0.5 or a named template; the chief gets it at 0.8 and then Refine doesn't start by itself; 0.5–0.8, or Jev failing with the name present, only highlights 🧑‍💼. `scripts/qa/jev-check.py` asks the real Jev the same questions (read from `Jev.java`) on a labelled set and writes a report; it costs about $0.002 per run. Refine (`TextModel`, 4,096 tokens; the model is the user's pick, prefs `refineModel`/`refineModelName` for OpenRouter, default `anthropic/claude-sonnet-5.5`, and `refineClaude` for Anthropic, default `claude-sonnet-5-5`; the picker filters OpenRouter's public `GET /models` to text-only output with `TextModel.catalog`, and offers `Anthropic.MODELS`, the current Claude models with their list prices; attachments as message parts, PDFs through OpenRouter's `file-parser` plugin) goes to `/chat/completions`, or, with an Anthropic key in the Vault, to Anthropic's `/v1/messages` (`Anthropic`, base URL `BuildConfig.ANTHROPIC_URL`, `-PanthropicUrl=`; plain HTTP with `x-api-key` and `anthropic-version: 2023-06-01`; effort `low`; `thinking: between_tools` only for Sonnet 5.5, which is the only one that accepts it; OpenRouter parts mapped to `image`/`document` base64 blocks). Any Anthropic failure retries through OpenRouter; the Activity step records `provider` and `fallback`. Anthropic's cost is the model's list price (`Anthropic.MODELS`; Sonnet 5.5 $2/$10 per MTok), stored as `anthropicCost` and kept out of `knownCost`, so note and month totals stay OpenRouter only. The fake OpenRouter also serves a small catalog at `/api/v1/models` (with an image model the picker must leave out), and `/v1/models` and `/v1/messages` (queue `anthropic`), and `device-test.sh` passes `-PanthropicUrl`. Dictate & Delegate writes the clipboard only on an explicit Copy or when Insert fails; `TalkAccessibility.insert` uses `ACTION_SET_TEXT` and falls back to a paste only when the app refuses that. Each response's `usage.cost` is what the note and Activity show; a missing cost stays unknown.

bb: `BbBridge` talks to bb's MCP server (plugin `bb--mcp`) with `Mcp` (Streamable HTTP, protocol 2025-06-18, answers as JSON or event stream). Everything goes through the `run` tool, whose JavaScript snippet calls the bb CLI: `bb thread spawn --project proj_personal --title "Chief of staff" --prompt-file -` to create the chief (it only gets `ChiefSkills.START`), `bb thread show` to adopt an existing thread, and `bb thread tell <id> --mode queue --message-file -` to send (queued behind a running turn; on an idle thread it starts one right away). Text always goes as `stdin`, a JSON string literal, never spliced into argv or code. Snippets have 25 s and never wait. Two connection modes: bb Connect (`https://<handle>.getbb.app/mcp`, OAuth 2.1 with PKCE in `BbOAuth`; endpoints from the resource and authorization-server metadata, client ID = the URL of `oauth/client.json`, redirect `talkrouter://oauth/callback` handled by `BbSignInActivity`, refresh on expiry or 401, revoke on sign-out) or a custom address with an optional bearer token. Release builds allow plain HTTP only to 127.0.0.1/localhost (`res/xml/network_security_config.xml`) for `adb reverse`. The chief notifies through ntfy itself (`curl … -H "Click: <link base>/threads/$BB_THREAD_ID" <server>/<topic>`). Each message to the chief ends with `[request: <id>]`; text to paste goes back as an ntfy message tagged `talkrouter-paste` and `req-<id>`, with a broadcast action (`app.driftdictation.COPY_CHIEF_TEXT`, extra `request`) for ntfy's Copy button (`BbBridge.pasteCommand`). `ChiefText` reads the topic's JSON stream while the panel waits and fetches a request's text for the Copy broadcast, which `TalkAccessibility` receives. Thread links open with `Browser.EXTRA_APPLICATION_ID`, so Chromium browsers reuse one tab. Thread links are `<link base>/threads/<id>`, the link base being `https://<handle>.getbb.app` or what the user entered. The speech-model catalog is bundled in `assets/models.json`; `Profile.OFFERED` lists the models whose word hints work.

`NotesPerfTest` (opt-in, `-e perf true`) seeds 2,000 notes (`seed`), logs how long home, All notes, search and opening a note take and scroll frame times under logcat tag `NotesPerf` (`measure`, run in a fresh `am instrument` so nothing is warm), and removes them (`clean`).

Debug-only hooks (absent in release because they check `BuildConfig.DEBUG`): launch extras `debugSeed` (sample notes) and `debugScreenshots` (lifts `FLAG_SECURE`). Debug builds also allow plain HTTP for the fake.

Main components: `DictationService` (capture, chunked transcription, the panel's session: Jev, Refine, the chief, Insert; recovery), `FloatingPanel` (the overlay: icon or buttons, wrapping to a second row when they don't fit), `TalkAccessibility` (volume key, Insert, replace in place, the Copy receiver), `Jev` (decisions), `ChiefText` (request IDs, the chief's text from ntfy), `AudioArchive` (retention), `Vault` (secrets sealed with a Keystore key: API keys, bb tokens, the ntfy topic; the non-secret `templates`, `transcript` and `progress` are kept plain in the `data` preferences and move there from the vault when first read), `HistoryStore` (versions/checkpoints as plain JSON in app-private SQLite, with a `recording` column for a note's versions; rows sealed by earlier versions are rewritten plain in the background at start, `HistoryStore.unseal`), `TextModel` (the Refine call), `OpenRouter` (the HTTP client), `BbBridge` / `BbOAuth` / `BbSignInActivity` / `Mcp` (bb), `Attachments`, `Templates`, `I18n` (translations), `MainActivity` (UI), `DictationTile` / `OverlayIcon` / `RecordActivity` (starting).

The chief's instructions are two bb user skills (`ChiefSkills`): templates in `assets/skills/chief-of-staff/SKILL.md` and `assets/skills/dictate-and-delegate/SKILL.md`, filled with the user's name (`{{NAME}}`, "the user" when empty), `{{NTFY_SERVER}}`, `{{TOPIC}}` and `{{LINK_BASE}}` (no Click header without one). Each filled file ends with `<!-- <name>-skill: <hash> -->`, the first 12 hex digits of the SHA-256 of the filled content: a changed template or placeholder gives another hash, so one comparison covers app updates and setting changes. `ChiefSkills.sync` compares the filled hashes and the app's versionCode with what was installed last (prefs `skillsInstalled`, `skillsCheckedVersion`); only when they differ, or on connect and **Check the skills in bb**, it reads bb's markers with the MCP `read` tool (`bb skill list`, then `bb skill show` for user-scope skills). If one is missing or different, it spawns "Dictate & Delegate: install skills" in Personal with both files verbatim in the prompt (MCP snippets can't write files), polls the markers every 3 s for up to 4 minutes, then archives the thread. It runs at app start (`onResume`), on connect, after a name, server or link change, and before creating or adopting a chief. The fake bb (`fake_bb_mcp.py`) answers `skill list` with its installed hashes, "installs" the files from an install thread's prompt at once (`/test/skills` presets them or makes the install stall) and accepts `thread archive`.

While the 📎's file picker is open (`AttachActivity` → `DictationService.picking`), the floating panel and the hands-free panel are taken off the screen and come back when it closes: pickers such as Android's photo picker ignore every tap while another app's window lies over the screen. Attachments for the chief: pasted text and text files go inline in the message; images (stored as JPEG) and PDFs go as attachments, images first (`Attachments.binaries`). `BbBridge.sendRequest` uploads each to bb's REST API, `POST <bb>/api/v1/projects/proj_personal/attachments` (multipart field `file`, the same call bb's own app and `bb project attachment upload` make; `<bb>` is the MCP address without `/api/v1/plugins/bb--mcp/http/mcp` or `/mcp`, or `https://<handle>.getbb.app` for bb Connect, with the same bearer token), and passes the returned paths to `bb thread tell … --image <path>` / `--file <path>`. MCP snippets can't carry binary (`bb.cli` stdin must be a string, `bb file write` is UTF-8), and bb's `run`/`read` tools take at most 100,000 characters of code (`inputSchema` maxLength; `BbBridge.CODE_LIMIT`, checked before sending). So when bb answers the upload with 401, 403, 404 or 405 (bb Connect does: the app's token is issued for `/mcp`), each file goes base64-encoded in parts of 80,000 characters, one `bb project attachment upload --client-file /dev/stdin` per part, named `<name>.partNNofMM.b64`, and the message asks the chief to join and decode them; files over 3 MB (`BASE64_MAX`) aren't sent that way but named in the message. Pasted text in a message is capped at 60,000 characters. A file that fails never stops the dictation. The bb step in Activity records `files`, `filesHow` (`upload`, `base64` or both), `uploadRefused` (the HTTP status) and `filesFailed`. The opt-in real check `PanelTest#realBbChiefSeesAnAttachedImage` takes `-e realBase64 true` to refuse the upload on purpose (`BbBridge.refuseUploads`). The fake bb serves the upload endpoint (`/test/config {"uploadStatus": 401}` refuses it), stores the base64 uploads, and lists both at `/test/uploads`.

Hands-free mode (`HandsFreeService`, `HandsFreeSession`, `HandsFree`, `Voice`): a foreground service (microphone and media playback) records 16 kHz PCM with `VOICE_COMMUNICATION` and the echo canceller, so a reply read aloud doesn't count as speech. `HandsFree.Segmenter` splits 20 ms frames into speech in three layers: a `HandsFree.Detector` says whether a frame is speech (today `LEVEL`, by its level; a model such as Silero can take its place), the frame must be `hfGate` (3×) louder than a noise floor that follows quiet frames, and a stretch only counts once it holds `hfTakeMs` (1 s) of such frames (`started`); shorter ones are `noise`, logged and dropped. 300 ms are kept before and after; a stretch ends after a short pause (`hfPauseMs`, 0.8 s, so a send or end word acts almost at once) and only its audio is transcribed (`AudioFiles.wav`), so each part costs once and silence never reaches the speech model. `HandsFree.endsWith` matches the send and end words at the end of the text (whole words, case, accents and punctuation ignored). With live transcription (`StreamingSpeech`), a send or end word at the end of the live text asks Jev at once, on the speech pool, while `SEND_QUIET_MS` (300 ms) of quiet after it is waited for; a send word sends only when Jev's done probability is at least `PHRASE_SEND_AT` (0.5) or Jev can't answer within `phraseJudgeMs` (3.5 s), an end word only with Jev's goodbye at `END_AT` (0.8). A send word Jev held back doesn't ask again while the live text stays the same (`heldPhrase`). Parts written down from their audio at a pause because the live text had none become the turn's words (`turnPrefix`), so a send word after the pause sends them too; live words of them that came while they were written down are dropped (only then: a drop with nothing live guesses at the next stretch). If you went on meanwhile, the next check decides. A send word Jev held back doesn't send when Jev then fails at the pause. When the stretch with the send word goes on after it, what the live text heard after it is taken into the next turn when the stretch ends (`takeRest`), followed by a pause check (or the send, with Send pressed). Each new connection is a new session at the provider (`StreamingSpeech.newSession`): AssemblyAI's `turn_order` starts at 0 again, so its turn counters start again too (kept, the new session's finals were taken for repeats and dropped), and live text the last session never finalised is kept. While a reply plays, `HandsFreeSession.frame` checks the microphone for barge-in instead of segmenting: for `ECHO_FRAMES` (0.7 s) after its audio starts it measures the reply's echo level (it then follows it), and `BARGE_FRAMES` (300 ms) above `BARGE_FACTOR` (2.5) times that, and above the speech floor, pause the reply (`Speaker.pause`) and capture a snippet (with 300 ms before) until the short pause. The snippet is transcribed: empty, or mostly the reply's words around the paused position (`echoOf`: 60 % of its words among the 30 before and 8 after), resumes the reply; anything else stops it, becomes the start of your turn (speech captured during the check is fed to the segmenter after it), and adds `[heard up to: "…"]` (`heardUpTo`: the last 8 whole words up to `Speaker.heardChars`, from the playback position minus 0.3 s, or Android's voice's `onRangeStart`) to your next message. Each decision is logged with its levels. After a reply ends normally, frames are dropped for `TAIL_MS` (800 ms) and the segmenter is reset, so its last word doesn't start your turn. The session keeps a floor (`OPEN`, `YOU`, `CHIEF`): a reply is read only on an open floor; while you hold it (a confirmed stretch, one being transcribed, unsent text or a send in flight) replies are held. Once the floor is yours a short stretch (`SHORT_MS`) counts, so a quick "over" isn't lost. When your turn is sent, held replies are dropped and the message gets `[didn't hear your reply: "<first 12 words>…"]` for each (`HandsFreeSession.missed`); a turn that comes to nothing releases the floor and the held reply is read. `[hands-free call started]` and `[hands-free call ended]` go to the chief when the mode starts and ends (the service stays in the foreground until the end is delivered, at most 5 s). A reply's audio is prepared (`Speaker.prepare`, the MP3 fetched) as soon as it arrives, while the floor stays open; the chief takes the floor only with a prepared reply, so reading starts only once audio is ready. A watchdog in `tick` gives a reading up when its audio hasn't started within `START_MS` (6 s) or runs `OVERRUN_MS` (3 s) past its length while the voice no longer says audio is playing (`Speaker.playing`: `MediaPlayer.isPlaying`, `TextToSpeech.isSpeaking`; at most `READING_CAP_MS`, 10 minutes, in all); a reply that didn't play counts as not heard and is noted in the next message like a dropped one. `Voice.play` first plays `WARM_MS` (0.5 s) of silence on the same `AudioAttributes` (an `AudioTrack` kept until the reply started), so a route that wakes with the first sound (Bluetooth, right after the microphone) loses silence instead of words, and holds transient audio focus with ducking while a reply plays. OpenRouter failing falls back to Android's voice; Android's voice failing (`speak` refusing, no engine) ends the reading at once. A transcription that fails gives the floor back. The status says "Listening · Chief is working…" while the chief works, since you can talk then; Send now shows whenever you can. Each message's note carries the call's ID (`call`), and `NoteList.withCalls` shows a call as one entry in All notes and on Home, with its total cost, opened to its messages. `seed` takes the audio of a dictation switched over with the floating panel's 📞 (through `RecordActivity`, which may start the microphone service). Each step goes to `handsfree.log` (Settings → Hands-free) and into the note of the message. Messages go with `BbBridge.sendHandsFree` and end with `[hands-free]` before the request ID; the dictate-and-delegate skill tells the chief to answer those with ntfy messages tagged `talkrouter-speak` and `req-<id>` (a first answer, then the final answer), which `ChiefText.Replies` reads from the topic's stream. `Voice` asks OpenRouter's `POST /audio/speech` for an MP3 (`hexgrad/kokoro-82m` with `af_heart` by default, or `elevenlabs/eleven-flash-v2.5`; a voice is required) and plays it, or uses Android's TextToSpeech; what a reply cost is looked up from OpenRouter's `GET /generation` with its `X-Generation-Id` (list price per character as a fallback) and charged to the note of the message it answers (`voiceCost`, a `voice` step). A media session takes the headset button; `HandsFreePanel` floats the call over other apps: started with 📞, where the dictation panel was (`AT_X`/`AT_Y` through `RecordActivity`), otherwise where it was last dragged (`hfPanelX`/`hfPanelY`). The fake OpenRouter answers `/audio/speech` with `scripts/fakes/reply.mp3`; `HandsFreeFlowTest` feeds frames instead of the microphone (`HandsFreeService.noMicrophone`), and its opt-in real check sends a hands-free message to a real test chief.
